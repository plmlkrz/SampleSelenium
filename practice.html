Three whiteboard-ready architectures. Trace the arrows top to bottom while saying the talk track out loud — the strongest interview move is sketching this while you explain it.

Spring Boot API framework REST Assured + Cucumber + Spring DI

Talk track: profiles pick the environment, DI owns the beans. Features state intent; step definitions delegate to the client layer — the API-side equivalent of page objects. Each core box has one reason to change: contract, payload shape, assertion logic, or schema. WireMock keeps per-service tests deterministic; the SQL helper reconciles what the API claims against what persisted.

Selenium UI framework this repo — POM + ThreadLocal driver

Talk track: tests describe behavior and assertions; page objects hide locators behind meaningful actions and return the next page. BasePage centralizes explicit waits so no test calls Thread.sleep. The ThreadLocal DriverManager gives each parallel thread its own browser, and a listener captures screenshots automatically on failure — the same suite runs serially or with parallel="methods".

Selenium BDD framework Cucumber layer on top of POM

Talk track: features are the business-readable spec — intent above the step-definition line, mechanics below. Hooks own the driver lifecycle around every scenario, so steps never touch setup. The scenario context (PicoContainer or cucumber-spring) carries state like an order ID between step classes without static variables, keeping parallel scenarios isolated. Tags slice one suite into smoke and regression runs.
